Why keys only

Login to Digits Cloud servers is by SSH key only. The private key stays on your machine; we never see or hold it. Only the public half is written to the server. Passwords get brute-forced; keys do not.

Creating a key

The same command on Linux, macOS and Windows (PowerShell). Use ed25519, and give the key a passphrase if you want protection should your machine be stolen:

bash
ssh-keygen -t ed25519 -C "laptop-2026"
output
Generating public/private ed25519 key pair.
Enter file in which to save the key (~/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Your public key has been saved in ~/.ssh/id_ed25519.pub

Print the public half and paste the whole line (it starts with ssh-ed25519 and ends with the comment) into the SSH key field when ordering:

bash
cat ~/.ssh/id_ed25519.pub
powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub

Careful. Never paste the file without .pub. That is the private key, and it must never leave your machine.

Adding a second key to a running server

Each key is one line in the user’s authorized_keys file. From a machine that already has access:

bash
ssh-copy-id -i ~/.ssh/id_ed25519_new.pub <user>@<ip>

Or by hand on the server: append the line to the file and set the permissions. sshd needs no restart.

bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo "ssh-ed25519 AAAA… comment" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Test the new key from a second window before closing the first session:

bash
ssh -i ~/.ssh/id_ed25519_new -o IdentitiesOnly=yes <user>@<ip>

Rotating or removing a key

Add the new key first and confirm it works, then delete the old line. The order matters: deleting first locks you out.

bash
nano ~/.ssh/authorized_keys

If you lose every key: we cannot recover your private key, but the browser console in the client panel gives you a session on the server itself, from which you add a new key. Details are in the browser console article.

A connection shortcut with ~/.ssh/config

Add the following block on your machine; the connection becomes ssh web1, and it stays alive across quiet networks:

~/.ssh/config
Host web1
    HostName <ip>
    User <user>
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30

Permission denied (publickey)

The message means the server rejected every key your machine offered. In order of likelihood: your machine offered a different key, the login name is wrong, or ~/.ssh permissions on the server are too open. Run the connection verbosely to see which key was offered:

bash
ssh -v -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes <user>@<ip>
